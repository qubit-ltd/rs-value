# `rs-value` 设计与实现评审（2026-07-11）

## 结论

`rs-value` 作为拥有所有权的动态值容器应继续独立存在，不应并回 `rs-datatype` 或 `rs-config`。`Value` 被 `rs-metadata` 作为元数据值使用，`MultiValues` 被 `rs-config` 作为配置属性承载；两者的真实消费边界已经足够明确。

需要进行一次有版本边界的语义收敛：明确空值、列表、非有限浮点和 wire format 的契约。当前 enum 既承担运行时容器又直接承担公共序列化协议，是最大的长期演进风险。

本评审中没有发现 P0。

## 做得好的部分

- `Value::get` 的严格匹配与 `Value::to` 的显式转换分层清楚。
- 借用 accessor、消耗型 `add`、`clear` 保留 Vec capacity 等基础 API 设计合理。
- 单值与多值容器共享类型体系和转换实现，避免了在上层重复实现转换逻辑。
- `rs-config` 和 `rs-metadata` 已有大量实际调用，说明这不是无消费方的抽象。

## 需要优先修复的契约问题

### P1：非有限浮点无法 Serde 往返

`Value` 和 `MultiValues` 允许 `NaN`、`+∞`、`-∞`，却直接 derive `Serialize/Deserialize`。当前 JSON 结果会把 `Value::Float64(NaN)` 写为 `{"Float64":null}`，再反序列化时失败；`rs-config` 的 JSON 投影也把非有限浮点固化为 `null`。

这会造成 metadata/config 的数据丢失，并且 `NaN` 还会破坏 `PartialEq` 的自反性。建议下一个不兼容版本默认拒绝非有限浮点；若业务必须支持，应使用明确、版本化的字符串编码，而不能静默写成 `null`。

### P1：单元素字符串列表被猜测为标量来源

`src/multi_values/multi_values_converters.rs` 对 `MultiValues::String` 在长度为 1 时走 `ScalarStringDataConverters`。开启分隔符后，`["a,b"]` 会解析为 `["a", "b"]`，但 `["a,b", "c"]` 会保留为两个原始元素。

列表语义因此取决于长度，而不是数据来源。建议删除 `len() == 1` 推断；由配置 source 显式标记“标量文本”或“已物化列表”，再选择是否拆分。

### P1：普通 `Value::to()` 是 metadata 热路径上的额外分配

每次 `Value::to()` 都构造拥有多个 `Vec<String>` 的默认 `DataConversionOptions`。当前探针中，`Value::Int32(42).to::<i64>()` 产生 7 次堆分配，而 `get::<i32>()` 无分配；`rs-metadata` 的 typed get 会走前者。

建议把默认 options 做成共享 `LazyLock`，并将布尔 literal 与分隔符改为静态借用切片或 `Cow`。这是一项直接影响真实读取热路径的优化。

## 需要在下个阶段处理的问题

### P2：两种空集合表示没有被正式建模

`Empty(DataType::Int32)` 与 `Int32(vec![])` 的 `data_type/count/is_empty/get` 等多数行为相同，但二者不相等、Serde 结果也不同。配置层又把所有 `is_empty()` 值当成 missing，导致“显式空列表”和“未设置”行为混淆。

应明确选择：

1. 无业务差异：构造、clear 和反序列化时统一规范化；或
2. 有业务差异：将 null 与 explicit empty 正式写入 API、默认值规则和文档。

### P2：运行时 enum 不应无版本地充当持久化协议

externally-tagged `Value` 已进入 metadata filter wire。新增 variant 会同时破坏下游穷举 match 和 wire 兼容；`IntSize/UIntSize` 还依赖目标架构。

建议新增固定宽度、版本化的 `ValueWireV1`；运行时 `Value` 与外部协议之间由显式 adapter 转换。若暂不拆分，至少冻结当前 schema、补全每个 variant 的 golden test，并明确平台整数不能跨架构持久化。

### P2：错误结构在批量转换时丢失

`DataListConversionError { index, source }` 会被压成 `ValueError::ConversionError(String)`，后续配置层无法可靠取得原始索引和底层 cause。建议保留结构化 `ListConversion { index, source }`，单值转换也透明保存 `DataConversionError` source。

### P2：公开 API 面大于当前消费面

`NamedValue`、`NamedMultiValues` 在其他 `rs-*` 生产代码中没有已知调用点，类型专用 setter/getter 数量也远多于实际使用的泛型入口。建议先做弃用评估或 feature 化，而不是继续扩大稳定 API。

## 建议的演进顺序

1. 明确并测试 NaN/Infinity、null、empty list、single scalar text 的语义。
2. 将 source 形态从容器长度中解耦，避免用启发式推断列表语义。
3. 分离 runtime value 与版本化 wire adapter，固定宽度处理跨平台整数。
4. 共享默认转换选项，随后再优化重复分配和 JSON clone 路径。
