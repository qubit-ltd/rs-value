## 3. RV-005：修正依赖下限

### 3.1 证据

- `Cargo.toml:129`：`bigdecimal = { version = "^0.4", optional = true }`。
- `src/identity/big_decimal_hash.rs:30`、`src/value_wire/value_wire_payload_ref_v1.rs:349,397`、`src/wire/internal/big_decimal_payload.rs` 和 preflight 使用 `as_bigint_and_scale()`。
- 上游 [0.4.6 源码](https://raw.githubusercontent.com/akubera/bigdecimal-rs/v0.4.6/src/lib.rs) 没有该方法，[0.4.7 源码](https://raw.githubusercontent.com/akubera/bigdecimal-rs/v0.4.7/src/lib.rs) 已提供借用 `Cow<BigInt>` 的版本。
- 评审时 `cargo metadata --locked --offline` 显示，依赖图中 `qubit-budget`、`qubit-datatype` 和本 crate 对 `bigdecimal` 都使用 `^0.4`，没有其他下限替本 crate 排除旧版本。

### 3.2 实现

根 `Cargo.toml` 的单行改为：

```toml
bigdecimal = { version = "^0.4.7", optional = true }
```

`^0.4.7` 保留后续兼容的 0.4.x 版本，并明确排除已知不支持的版本。根 lockfile 当前解析版本若满足新约束，不更新 lockfile。`fuzz/Cargo.toml` 的直接 `bigdecimal = "0.4"` 与根路径依赖共同解析，根下限已能形成约束，默认不改它。

### 3.3 最低版本验证

在仓库外创建可丢弃消费者，使用路径依赖指向当前 rs-value，并直接指定 `bigdecimal = "=0.4.7"`。在自己的独立 target 目录分别验证 `big-decimal` 和 `big-decimal,json,converter` 两组 feature。执行 metadata 核对实际图中唯一的 bigdecimal 版本就是 0.4.7，不能只看清单中的精确版本声明。

消费者只用于验证本 crate 的依赖下限，不编译或测试 rs-config、rs-metadata。其 lockfile 与 target 都在临时目录中，不修改项目 lockfile，也不增加常驻消费者工程或 CI 工作流。

若精确版本失败，先区分方法缺失、传递依赖不兼容、网络/工具链等原因。只有确实需要更高 bigdecimal 版本时才提高到验证通过的最小版本并记录证据；不得回退到已知不支持版本或随意改动无关依赖。

### 3.4 兼容性与迁移

运行时行为和 API 不变。依赖解析范围收紧：使用旧 lockfile 的应用应允许更新 bigdecimal 到至少 0.4.7；若应用自己精确固定更旧版本，应解除或提高该固定值。当前直接下游 rs-config、rs-metadata 仅在启用相应大数 feature 且锁定旧 bigdecimal 时受影响，无需改调用代码。无需更改 Wire 版本或运行时类型。

## 4. RV-006：扩展原始输入 fuzz 的有效探索范围

### 4.1 当前局限

`fuzz/fuzz_targets/bounded_value_wire_v1.rs:21–46` 将输入上限固定为 94 字节，超过即断言输入预算失败。结构预算保持默认深度 64、节点 100000、序列项 4096、map 项 4096，因此此目标实际上无法触及这些结构限制。

另外两个目标分别从有效类型化值进行往返和检查编码 preflight，不能覆盖较长畸形原始文档。现有 `tests/value_wire/value_wire_v1_tests.rs` 已覆盖部分固定结构限制；本方案增加 fuzz 组合探索，不重复建设生产测试框架。

### 4.2 选定结构

| 路径 | 变更与职责 |
| --- | --- |
| `fuzz/src/bounded_wire_input.rs` | 新建：执行三个原始输入档位及成功解码后的往返断言 |
| `fuzz/src/lib.rs` | 增加该辅助模块的导出，供目标与确定性测试复用 |
| `fuzz/fuzz_targets/bounded_value_wire_v1.rs` | 保持现有目标名，入口转调 helper |
| `fuzz/tests/bounded_wire_input_tests.rs` | 新建：证明长文档到达宽档位、结构限制可触及、既有超限检查保留 |
| `fuzz/corpus/bounded_value_wire_v1/long-string` | 新建：长于 94 字节的合法文档 |
| `fuzz/corpus/bounded_value_wire_v1/nested-array` | 新建：嵌套 JSON payload |
| `fuzz/corpus/bounded_value_wire_v1/duplicate-key` | 新建：较长文档中的重复键 |
| `fuzz/corpus/bounded_value_wire_v1/malformed-tail` | 新建：较长文档中的畸形尾部 |

不更换 libFuzzer、不新增 fuzz binary、不调整 workflow。现有 workflow 的 `-max_len=4096` 足以支持宽档位。新增文件使用已核对为不存在的路径；若实施时同名文件已出现，先保留并核对，不覆盖用户内容。

### 4.3 三档执行策略

每次原始输入执行：

1. **兼容小档位：** 原样保留 `max_input_bytes=94`。长度超过 94 时必须为 `InputBytes` 预算失败，而非仅检查任意 `Budget`。该档位返回后继续执行宽档位，不能结束整个 fuzz 回调。
2. **宽档位：** `max_input_bytes=4096`，结构预算沿用 V1 默认 profile，允许较长合法和畸形文档进入解析。超出 4096 的输入按输入预算拒绝，不截断输入制造伪成功。
3. **结构变化档位：** 同样允许 4096 字节原始输入；只将 depth、nodes、sequence_items、map_entries 分别设为有限的变化值，其余值限制沿用默认值。选择集合为 depth `{0,1,4,8,16,64}`、nodes `{0,1,8,32,128,4096}`、sequence_items/map_entries `{0,1,2,8,32,4096}`。用输入全体字节分成四组后的 wrapping 累加值分别选取，避免控制只依赖固定 envelope 前缀。原始 JSON 本身不消费或剥离控制头，保持既有语料格式。

每档使用全新 decoder/session，不把小档位或失败档位的消耗带入其他档位。预期拒绝类别保持 `Syntax`、`InvalidJson`、`Budget`、`UnsupportedVersion`，其他错误继续触发失败，不能宽泛吞掉全部错误。

### 4.4 往返 oracle 与辅助接口

helper 的唯一对外入口：

```rust
pub fn check_input(data: &[u8]) -> bool
```

返回值表示宽档位是否成功解码，专供确定性回归验证长输入确实到达解析；fuzz 入口忽略返回值。三个档位的成功解码都执行往返 oracle，而不是仅验证宽档位。

成功解码结果使用 64 KiB 输出限制编码，然后使用 64 KiB 输入限制、V1 默认 value profile 解码并断言 identity 相等。往返不用原先的紧结构档位，以免规范化输出的尺寸变化造成无关失败；结构预算检查仍由各自原始解码完成。4 KiB 原始输入的默认有界解码只会产生受默认 profile 限制的值；64 KiB 是测试输出保护上限，不修改生产默认值。若有效输入触发输出上限，保存样本并调查输出放大及 oracle 边界，不能直接吞掉编码错误或提高上限掩盖问题。

### 4.5 确定性回归与语料

- 94、95、4096、4097 字节输入边界：通过小档位/宽档位分别检查 `InputBytes` 分类；用合法文档加 JSON 空白补齐，避免仅测试无效字节。
- 合法 256 字节字符串文档：旧目标只会输入拒绝，新 `check_input` 必须返回 true，并通过往返。
- 深度、节点、序列项、map 项：分别构造仅该维度超限且其他维度足够的输入，断言对应 `JsonResource`；提高对应上限后成功。另对选择器的所有档位做可达性测试。
- 64 层以上的嵌套 JSON：宽档位按默认 depth 拒绝，验证资源边界而非依赖 parser 固定递归上限。
- 重复键与畸形尾部：长度均超过 94 字节且小于 4096，宽档位应分别为 schema/重复键拒绝和语法拒绝；断言类别，不依赖完整错误字符串。
- 既有四个 corpus 文件保留；新语料不携带控制头，不含敏感内容。

若确定性测试暴露新的生产缺陷，记录复现与影响，再按实际缺陷决定直接相关修复；不能以 fuzz 扩展名义批量修改生产 parser。尚未发现的缺陷不列为本方案已确认成果。
